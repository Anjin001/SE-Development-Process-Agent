# 需求录入与赛马出案

**负责人：陈林赟** · `feat/intake-race`

## 交付边界

本模块从用户输入 Markdown 开始，将同一个需求版本和两份独立小组草案交给评审与整合模块。正式评分、全体讨论、融合决定和规格确认由洪少炫负责。工作台原型供张艺薷接入时参考。

## 流程与界面

| 阶段 | 系统动作 | 人的动作 |
|---|---|---|
| 需求录入 | 保留原文，生成需求条目、章节和行号 | 编辑 Markdown，确认快照后检查来源。改动时重新确认，形成新版本 |
| 独立构思 | 每个角色只读需求快照、角色和路线。每人交一条构思与风险 | 可启动赛马，查看两组状态 |
| 组内收敛 | 组内先汇总想法，再提出一轮质疑，最后生成有引用的草案。A 组从核心规则切入，B 组从用户体验和异常流程切入 | 一组失败时单独重试。另一组结果保留 |
| 评审交接 | 两组都成功后统一展示，保留独立想法、组内质疑和需求依据，可导出交接 JSON | 对照两组方向和待确认问题，将材料交给评审 |

演示沿用工作台的顶部阶段导航、中部内容、右侧主理提示。按当前 v2 契约固定 A/B 两组，每组两个不同职责的角色。之前方案中的动态分组和第三组作为扩展点保留。问题句和明确的待澄清章节在模拟草案中保留为问题，人可回到输入补充信息。

## 模块接口

- `extract_items(markdown)` 返回 v2 条目列表。Markdown 标题、列表项和段落保持相对原文行号，代码块不作为需求。解析为本地规则首版，提取结果由人确认。
- `build_snapshot(markdown, requirement_id, version)` 组合需求快照，版本由调用方分配，原文照存。
- `generate_draft(requirement, group_id)` 返回 v2 Draft。评审交接结构为 `{requirement, drafts: [A, B]}`。
- `run_group(requirement, group_id, agent=...)` 同时返回独立想法和质疑记录。可替换的 Agent 回调按 `idea → challenge → draft` 调用。独立构思不读取其他人的想法；质疑和草案阶段只读本组材料。每次调用接收独立上下文副本。返回草案必须引用有效需求 ID。
- v1 的 `intake()` 与 `race()` 继续服务原 MVP。正式 v2 服务负责持久化、分组状态、超时和重试。正式模型接入时每次调用使用独立会话，沿用同一交接格式。

## 运行与演示

```bash
python -m se_agent.intake_preview --port 8001
```

浏览器打开 http://127.0.0.1:8001。确认默认需求，勾选「模拟 B 组首次中断」，然后启动。A 完成后只显示提交状态，点击「重试 B 组」后才公开两份草案。展开独立想法，最后下载 JSON。编辑需求后需重新确认，新结果使用新版本。

本轮交付本地工作台与规则模拟；模型调用、数据库和正式 v2 HTTP 尚未接入。回调和模块的数据形状可以直接用于下一轮联调。
