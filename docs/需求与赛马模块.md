# 需求录入与赛马出案

**负责人：陈林赟** · `feat/intake-race`

## 交付边界

本模块从用户输入 Markdown 开始，将同一个需求版本和两份独立小组草案交给评审与整合模块。正式评分、全体讨论、融合决定和规格确认由洪少炫负责。工作台原型供张艺薷接入时参考。

## 流程与界面

| 阶段 | 系统动作 | 人的动作 |
|---|---|---|
| 需求录入 | 保留原文，生成需求条目、章节和行号 | 编辑 Markdown，确认快照后检查来源。改动时重新确认，形成新版本 |
| 独立构思 | 每个角色只读需求快照、角色和本组提示词。每人交一条构思与风险 | 编辑 A/B 提示词，按需增加或移除额外小组后启动 |
| 组内收敛 | 组内先汇总想法，再提出一轮质疑，最后生成有引用的草案。默认 A 组从核心规则切入，B 组从用户体验和异常流程切入 | 一组失败时单独重试，其他小组结果保留 |
| 评审交接 | 参赛组都成功后统一展示，保留提示词、独立想法、组内质疑和需求依据 | 对照各组草案，导出正式 A/B 交接或全部草案 |

界面使用左侧两级目录、中部内容与右侧主理提示。二级目录可进入原文与快照、提示词与分组、小组进度、草案对照和交接下载。赛马启动时记录每组实际使用的提示词。要调整分组或提示词，可在同一需求版本上重新开始。问题句和待澄清章节在模拟草案中保留为问题。

## 模块接口

- `extract_items(markdown)` 返回 v2 条目列表。Markdown 标题、列表项和段落保持相对原文行号，代码块不作为需求。解析为本地规则首版，提取结果由人确认。
- `build_snapshot(markdown, requirement_id, version)` 组合需求快照，版本由调用方分配，原文照存。
- `generate_draft(requirement, group_id)` 返回 v2 Draft。评审交接结构为 `{requirement, drafts: [A, B]}`。
- `run_group(requirement, group_id, prompt=..., agent=...)` 同时返回独立想法和质疑记录。可替换的 Agent 回调按 `idea → challenge → draft` 调用，各阶段都收到 `group_prompt`。A/B 未传提示词时使用各自的默认值，新增组须提供提示词。独立构思不读取其他人的想法；质疑和草案阶段只读本组材料。每次调用接收独立上下文副本。返回草案必须引用有效需求 ID。
- v1 的 `intake()` 与 `race()` 继续服务原 MVP。正式 v2 服务负责持久化、分组状态、超时和重试。正式模型接入时每次调用使用独立会话，沿用同一交接格式。

## 运行与演示

```bash
python -m se_agent.intake_preview --port 8001
```

浏览器打开 http://127.0.0.1:8001。确认默认需求，勾选「模拟 B 组首次中断」，然后启动。A 完成后只显示提交状态，点击「重试 B 组」后才公开两份草案。展开独立想法，最后下载 JSON。也可以先编辑两组提示词，添加 C 组，再启动赛马。全部草案文件包含各组提示词，正式 v2 评审文件仍按现有契约交接 A/B 两组。编辑需求后需重新确认，新结果使用新版本。

本轮交付本地工作台与规则模拟。模拟结果记录自定义提示词，真实模型接入回调后会读取本组提示词生成内容。数据库和正式 v2 HTTP 尚未接入。回调和模块的数据形状可以直接用于下一轮联调。
