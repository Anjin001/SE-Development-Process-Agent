# 正式联调接口契约 v2

本文定义六条分支下一轮的共同目标。仓库当前可运行的是 v1 模拟链路。v2 尚待实现，接口以本文和 [联调样例](../examples/v2/scenario.json) 为准。模块在 v2 入口接入之前，保留现有模拟回归。

## 1. 记录与版本

| 表示 | 规则 |
|---|---|
| 字符串 ID | 项目内稳定，区分大小写。需求、规格、计划、任务各自有 ID 空间。运行 ID 在项目内唯一，尝试 ID 在运行内唯一 |
| 版本引用 | `{"id":"SPEC-01","version":1}`。版本为从 1 开始的整数，旧版本可读。提交或确认后正文及结构化决策不可覆盖，审核状态和确认元数据按各自章节更新 |
| 修订号 | `revision` 是可变记录的并发控制整数。客户端提交看到的修订号，服务端原子比较。与内容版本分别使用 |
| 时间、路径 | 时间为 UTC 的 ISO 8601 字符串，耗时及估时为非负整数秒。仓库内相对路径统一用 `/`。未知时间用 `null` |
| 字段 | 下表所列均为必填，标明可空者用 `null`。空列表用 `[]`。允许新增可选字段，客户端忽略未知字段 |

### 模块调用边界

v2 模块函数接受和返回普通 JSON 兼容对象。HTTP 层解析请求和身份，存储层分配记录 ID 和版本。现有 v1 函数和 HTTP 路径继续用于模拟回归。下表使用新函数名，v2 可先经独立适配器接入。

| 所有者 | v2 函数入口 | 责任边界 |
|---|---|---|
| 陈林赟 | `extract_items(markdown) -> RequirementItem[]`、`generate_draft(requirement, group_id) -> Draft` | 提取原文引用，单组调用只读取需求和本组身份。服务层保存需求和赛马结果 |
| 洪少炫 | `evaluate_draft(requirement, draft) -> Evaluation`、`propose_spec(requirement, drafts, evaluations, selection) -> {markdown,decisions,open_items}` | 评估单组草案，生成整合草稿。服务层保存编辑稿和处理确认 |
| 乔璐脉 | `decompose_tasks(confirmed_spec) -> Task[]` | 生成任务。编排服务绑定规格与仓库基线、生成 Plan 并校验；分解模块从该 Plan 导出文件 |
| 朱新棋 | `validate_plan(plan, confirmed_spec) -> None`、`schedule_plan(plan) -> ScheduleEntry[] or None` | 管理计划、运行、状态和存储。Worker 领取、续租、回报由编排器适配层连接 |
| 胡子昂 | `execute_task(request) -> WorkerResult` | 执行和回报单次尝试。编排器分配尝试、负责放行和调度 |
| 张艺薷 | §6 的 HTTP 接口 | 先以 JSON 样例完成视图。正式接入后由后端返回已生效的版本与状态 |

## 2. 需求、赛马与规格

| 记录 | 关键字段 |
|---|---|
| Requirement | `id`、`version`、`markdown`、`items[]`。每项含 `id,title,text,source`。`source` 含 `section,start_line,end_line`，行号从 1 开始，含首尾，基于保存的原文 |
| Draft | `id`（A 或 B）、`requirement_ref`、`title`、`summary`、`claims[]`。每条主张含 `id,text,requirement_ids` |
| Evaluation | `draft_id`、`criteria[]`。三个维度为 `value,feasibility,cost`，每项含 `criterion,score,reason,claim_ids`。分数为 1–5 的整数，成本分越高越省 |
| Specification | `id,version,status,requirement_ref,selection,markdown,decisions,open_items,confirmed_by,confirmed_at`。状态为 `draft/confirmed`。未确认时后两项为空，确认时由服务端记录 |
| Decision | `id,scope,choice,reason,requirement_ids,draft_ids`。其中 `choice` 为最终规则文本，`draft_ids` 允许 A、B 或两者 |
| OpenItem | `id,question,blocking,affected_requirement_ids,resolution`。未解决时 `resolution=null` |

A、B 两组读取同一个需求版本，在提交前无法读取对方草案。评审先独立写分项依据，再进入整合。评分负责暴露取舍，选 A、选 B 或融合由负责人确认。确认前可修订规格正文与决策，服务端拒绝引用不存在的需求或草案。正文和结构化条目同时保留，任务分解以已确认的结构化决策为依据，并保留正文引用。同一项目使用一个规格 ID，提交草稿、保存人工编辑都生成新版本。确认只改变最新草稿的状态及确认元数据。确认前已有新版本或绑定需求已更新时返回 `VERSION_CONFLICT`。`selection` 记录草稿以 A、B 或融合作为起点，最终决策以实际保存的结构化条目为准。

阻塞型未决项可以随规格确认。分解器把它挂到受影响任务，运行时只拦住这些任务及其下游。同一未决项影响多个任务时，每项任务独立补充，相同值可由界面反复提交。若补充信息改变已确认决策，提交新规格和计划版本，以新运行生效。普通实现细节可作为带审计记录的任务补充输入。

## 3. 任务与编排

| 记录 | 关键字段 |
|---|---|
| Plan | `id,version,spec_ref,base_commit,max_parallel,tasks`。`base_commit` 是目标仓库完整提交号，模拟模式可空。`max_parallel` 是正整数 |
| Task | `id,title,phase,requirement_ids,decision_ids,open_item_ids,depends_on,role,write_paths,outputs,estimate_seconds,review_required,completion_condition` |
| 输出定义 | `outputs[]` 每项含 `id,kind,path`。`kind` 为 `git_commit/text`，文本路径可空 |
| 排期条目 | `task_id,early_start_seconds,early_finish_seconds,critical`。计划相对起点为 0。有任务估时缺失时，整份计划的排期置空，仍可画依赖图 |

`depends_on` 是直接前置任务 ID 列表，去重且不得包含自身。任务可有多个规格来源，引用必须来自绑定版本。任务按 `phase` 字符串分组。输出 ID 在任务内唯一。每项至少有一项输出和一条完成条件。估时为正整数或 `null`，审核开关为布尔值。分解模块输出 `workflow.json` 并由同一记录生成 `task.md`。编排入口校验任务 ID、来源、前置、自环、环和路径合法性，返回可定位的错误，环要给出按前置到下游方向的闭环路径。拓扑顺序与输出任务数组位置无关。写入限制按文件路径或目录前缀匹配，拒绝绝对路径和包含 `..` 的路径段。目录前缀必须按路径段匹配，避免把 `app` 与 `app2` 判成冲突。

规划视图先按 DAG 算关键路径，再按并发和写入冲突算排期。并列就绪任务按任务 ID 稳定排序。排期条目中的起止秒数包括并发槽和写入冲突造成的计划等待，`critical` 仍表示按纯依赖算出的关键路径。一个运行内，同时写同一文件或相互包含的目录时串行派发。即使各自使用 worktree，汇合时也要显式合并上游提交。启动绑定规格、计划和基线；改计划写入新版本，修改已运行任务的依赖不影响旧运行。

## 4. 运行、任务状态与派发

运行记录包含 `id,plan_ref,mode,dispatch,state,revision,started_at,ended_at,latest_event_seq,tasks,findings`。`mode` 为 `auto/manual`，`dispatch` 为 `active/paused`，`state` 为 `active/completed`。对外状态变更的每次事务将 `revision` 递增一次并写事件。续租只更新内部到期时间，幂等回放不修改状态或游标，`latest_event_seq` 跟随最后一个已提交事件。任一任务失败、待审或待输入期间，运行仍为 `active`，便于继续独立分支。全部任务 `done` 后结束。

| 任务状态 | 进入条件 | 允许推进 |
|---|---|---|
| `waiting` | 前置尚未放行，或创建运行、重试、补输入后等待重新判定 | 前置全部放行且输入齐备进入 `ready`；缺输入为 `input_required`；失败祖先导致 `blocked` |
| `ready` | 前置和输入已满足 | 获取并发槽和写入资源后，事务内领取为 `running` |
| `running` | 分配唯一尝试号并持久化 | 回报后进入 `review/done/failed`，缺输入进入 `input_required` |
| `review` | 成功回报需人工审核 | 批准、批准修订后为 `done`；退回为 `failed` |
| `failed` | 失败、超时或人工退回 | 显式重试回到 `waiting`，下次领取产生新尝试 |
| `input_required` | 缺少输入或有阻塞型未决项 | 补齐当前缺项后回到 `waiting` |
| `blocked` | 有直接或间接失败祖先 | 该原因消除后重新判定 |
| `done` | 必需产物均通过并放行 | 终态；内容需要变更时创建新运行 |

`RunTask` 含 `task_id,state,attempts,artifacts,blockers,missing_input_ids,review_records`。`blockers[]` 含 `code,ref_id,message`。前置仍在执行或审核时显示 `UPSTREAM_RUNNING/UPSTREAM_REVIEW` 等等待原因。多个原因可并存。先判断失败祖先，再判断未完成前置，最后判断该任务自己的输入。只有已经进入 `input_required` 的任务可补输入。可以分次提交当前缺项，缺项全部补齐后重算就绪状态；入参含非缺项 ID 时整次拒绝。Worker 发现新缺项时，缺项 ID 使用本任务范围内稳定的标识符，记录对应问题。暂停停止所有新领取并清空未消费的手动名额，允许已启动尝试回报；恢复后重新判断就绪。手动模式每次推进领取不超过可用槽的一批任务，自动模式由调度循环领取。

SQLite 事务同时写状态、产物引用、尝试和事件。尝试包含 `id,number,state,created_at,started_at,ended_at,error,input_refs`。尝试状态为 `running/succeeded/failed/input_required`。租约到期时间在存储层维护。`input_refs` 是已领取输入的 `{id,version,commit_sha}` 列表。编排器内部适配层提供 `claim(run_id, worker_id) -> WorkerRequest or None`、`renew(run_id, attempt_id, worker_id) -> lease_until`、`report(run_id, worker_id, result) -> Run`。续租和回报匹配当前尝试和领取者。手动模式 `step` 将本批可派发任务固定为待领取名单，再由 `claim` 消费；名单未取完时再次 `step` 返回 409。重启后保留未到期尝试，过期时记 `WORKER_TIMEOUT` 并释放并发槽。旧尝试回报不可推进当前状态，以运行和尝试 ID 查找先前已受理的 Worker 回报。同一 Worker 的完全相同回报先按重放处理，其余不匹配当前尝试、领取者或租约的回报返回 `STALE_ATTEMPT`。

## 5. Worker 调用与人工交付

编排器派发由 Runner 消费。首轮保留编排器注入模拟 Runner 的入口，真实 Worker 沿用相同请求和回报形状。

| 方向 | 字段 |
|---|---|
| WorkerRequest | `project_id,run_id,attempt_id,task,spec_ref,spec_context,base_commit,workspace_id,inputs,supplied_inputs`。模拟时 `base_commit` 可空。真实 Worker 由 `workspace_id` 解析服务端分配的工作目录。`spec_context` 包含本任务关联的 `requirements,decisions` 完整条目和 `open_items`。`inputs` 为直接前置的已批准 Artifact 列表，`supplied_inputs` 为缺项 ID 到文本的映射 |
| WorkerResult | `attempt_id,status,artifacts,error,provider,model,usage,checkout_commit,started_at,ended_at`。`status` 为 `succeeded/failed/input_required`。成功时 `error=null`，每个任务输出恰有一条候选产物。候选产物只含 `output_id,kind,commit_sha,changed_paths,content`，编排器登记后再补充 Artifact 的 ID、版本及状态。`started_at`、`ended_at` 为尝试时间；工作区准备失败也要回报结束时间。`checkout_commit` 是纳入上游后、本次任务开始前的完整 SHA。模拟执行或尚未完成工作区准备时为 `null`。失败或缺输入时产物为空，保留结构化错误 |
| 错误 | `code,message,retryable,details`。Worker 以 `WORKER_TIMEOUT/MERGE_CONFLICT/MISSING_INPUT/EXECUTION_FAILED/OUTPUT_INVALID` 区分原因。缺输入时 `details` 必须含 `item_ids` 与 `questions`，后者是缺项 ID 到问题文本的映射 |
| 用量 | `usage` 为 `{input_tokens,output_tokens}` 或 `null`。模拟时用量与 `model` 为空，`provider="mock"` |
| Artifact | `id,version,task_id,attempt_id,output_id,kind,origin,status,based_on_version,commit_sha,changed_paths,content`。`origin=agent/human`，`status=draft/approved/rejected`。Git 产物提交号必填、文本为空。文本产物反之，路径列表为空 |
| Review record | `task_id,decision,expected_versions,approved_versions,note,actor_id,created_at`。操作者取服务端会话身份，提交时固定到该版本 |

首轮真实集成使用同一 Git 对象库下的多个 worktree，目标仓库由服务端配置。真实执行先从绑定基线创建本次尝试的独立分支，再按 `task_id,output_id` 升序纳入已批准的直接上游提交。上游提交包含该任务执行时纳入的更早依赖。Runner 保留纳入后的起点，校验本任务路径时只比较从该起点到任务提交的差异。工作区无法读取批准提交或合并冲突时，回报错误，保留已提交结果供处理。产物在运行结束后仍须可读取。Runner 将候选提交保留在服务端管理的 Git 引用上，编排器核验提交可达性、输出完整性、输出提交与 `checkout_commit` 的祖先关系、必需上游 SHA 是否已纳入，以及变更路径范围。下游请求保存具体产物版本及 Git SHA，后续查询能从尝试追溯实际消费的内容。模型路由、凭证和本地绝对路径留在执行端。

人工可以批准原稿、提交修订并批准、退回，备注随记录保存。批准原稿时沿用该内容版本，修订产生下一内容版本，原稿保留。产物审核状态是独立的放行元数据。产物 ID 在运行内唯一，同一任务同一输出重试沿用该 ID 并递增版本。`based_on_version` 在人工修订时指向原稿，其余为空。Git 修订由有权限的成员在服务端保留该尝试的工作区形成新提交，再提交 SHA。修订提交须基于被审提交，服务端重新核验路径、提交祖先关系和可读性。多产物任务按一项任务整体放行。`expected_versions` 必须覆盖当前全部待审版本，`revise` 可修改其中一项或多项，剩余原稿随该次审核批准。只有全部必需输出通过才释放下游。无需人工审核的任务由编排器校验后直接批准。退回后可重试，保留原尝试和历史版本。已经放行的产物发生变更时创建新运行，且可追溯旧下游使用的版本。

## 6. 工作台 HTTP v2

所有路径挂在 `/api/v2`。成功返回 JSON。创建资源为 201，接受后台赛马为 202，读取和已生效动作返回 200；后台领取和执行用事件持续报告。项目快照固定包含 `id,stage,requirement,race,drafts,evaluations,specification,latest_plan_ref,runs,findings`。`stage` 为 `intake/race/specification/planning/execution/completed`，按当前有效产物推导。`race` 是当前需求版本的赛马进度，未创建时为 `null`，其余为 `{requirement_ref,groups}`，每组 `{group_id,state,error}`，状态为 `pending/running/completed/failed`，失败时 `error={code,message}`，其余为 `null`。`drafts` 可包含已经成功的一组，两组完成后才进入方案整合。`runs` 为 `{id,plan_ref,state,started_at,ended_at}` 的列表。各组只有草案和分项评审都持久化后才标记 `completed`。重试保留该组已成功步骤，并从失败步骤继续。无规格或计划时对应字段为空，列表无数据时返回空列表。计划接口统一返回 `{plan,schedule}`，其中 `schedule` 为排期列表或 `null`。项目写操作需要成员身份，启动、规格确认和产物审核需要项目负责人或授权角色。开发环境可用固定测试身份，前端提交体不传操作者字段。越权返回 403。

| 方法与相对路径 | 请求 | 响应 |
|---|---|---|
| POST `/projects` | `{markdown}` | 完整项目快照 |
| GET `/projects/{project_id}` | 无 | 完整项目快照 |
| POST `/projects/{project_id}/requirements` | `{expected_version,markdown}` | 新需求版本及项目快照。之前草案和规格保留历史，新赛马读取新版本。该动作返回完整项目快照 |
| POST `/projects/{project_id}/race` | `{requirement_version}` | 接受任务后返回 202 和项目快照。前端轮询项目。只领取未开始或失败组；同版本正在运行的组不会重复领取 |
| POST `/projects/{project_id}/specifications` | `{requirement_version,selection,expected_version}`，编辑时再传完整的 `markdown,decisions,open_items` | 两组完成后才可生成待确认版本。首次 `expected_version=0`，未传编辑内容时由整合模块提出草稿 |
| GET `/projects/{project_id}/requirements/versions/{version}` | 无 | 指定需求版本 |
| GET `/projects/{project_id}/specifications/{id}/versions/{version}` | 无 | 指定规格版本 |
| POST `/projects/{project_id}/specifications/{id}/versions/{version}/confirm` | `{}` | 已确认规格 |
| POST `/projects/{project_id}/plans` | `{spec_ref,base_commit}` | 计划和排期。仅接受已确认规格 |
| GET `/projects/{project_id}/plans/{id}/versions/{version}` | 无 | 计划和排期 |
| PATCH `/projects/{project_id}/plans/{id}` | `{expected_version,max_parallel?,tasks?}` | 新计划版本及排期。传 `tasks` 时提交完整任务列表，校验失败则整次不生效 |
| POST `/projects/{project_id}/runs` | `{plan_ref,mode}` | 已启动运行。同一项目允许一个活动运行。引用必须是项目当前最新计划版本，并绑定当前需求版本下已确认的规格 |
| GET `/projects/{project_id}/runs/{id}` | 无 | 运行快照、任务、尝试、产物与阻塞原因 |
| GET `/projects/{project_id}/runs/{id}/events?after=0&limit=100` | 无 | `{items,next_after,has_more}`，升序，从严格大于 `after` 的序号开始 |
| POST `/projects/{project_id}/runs/{id}/actions/{action}` | 见下表 | 更新后的运行快照 |

动作请求均带 `expected_revision`。所有写请求带 `Idempotency-Key`；服务端按项目、HTTP 方法与路径、身份和 key 存结果。创建项目尚无项目 ID 时，以项目集合路径作为范围。相同 key 与相同请求重放原结果。同 key 内容不同返回 409。先校验是否重放，再校验新操作的版本。网络重试沿用原 key。收到版本冲突后刷新，再构造新操作并生成新 key。

| 动作 | 附加参数 |
|---|---|
| `pause/resume/step` | 无。仅手动且未暂停时可以 `step` |
| `retry` | `task_id` |
| `supply-input` | `task_id,values`，其中 `values` 是当前缺项 ID 到非空文本的映射 |
| `review` | `task_id,decision,expected_versions,revisions,note`。决定为 `approve/revise/reject`，预期版本为产物 ID 到版本号的映射。修订字段是产物 ID 到 `{content}` 或 `{commit_sha}` 的映射。批准原稿或退回时 `revisions={}`。退回备注必填 |

错误统一为 `{"error":{"code":"...","message":"...","details":{}}}`。400 表示请求格式或字段类型错误；404 表示引用不存在；409 表示 `VERSION_CONFLICT/INVALID_STATE/IDEMPOTENCY_CONFLICT/STALE_ATTEMPT`。前三类也由 HTTP 返回，`STALE_ATTEMPT` 用于编排器的 Worker 回报适配层；422 表示 `PLAN_CYCLE/INVALID_REFERENCE/INVALID_OUTPUT` 等业务校验失败。`VERSION_CONFLICT` 返回适用的 `current_version` 或 `current_revision`，审核冲突同时给出 `current_versions`。422 返回字段路径、ID 或循环路径。

事件记录含 `seq,type,run_id,task_id,attempt_id,created_at,payload`。该流提示前端重新读取快照，具体数据以快照为准。没有附加数据时 `payload={}`。运行级事件的任务和尝试可空。首轮事件包括 `run.started/run.paused/run.resumed/run.completed`、`task.dispatched/task.failed/task.input_required/task.input_supplied/task.retry_requested`、`artifact.submitted/artifact.approved/artifact.rejected`。每个运行的 `seq` 从 1 连续递增。`next_after` 为此次最后一条事件的序号，无事件时等于请求的 `after`。前端先拉快照，再从 `latest_event_seq` 轮询；事件到达时刷新相关快照，按 `seq` 去重。甘特图使用计划秒数与各次尝试起止时间，审核等待单独展示。依赖图、甘特图、任务配置和审阅页共享选中任务。

主理 AI 提示与运行状态分开保存。每条提示至少含 `stage,code,severity,summary,evidence_refs,affected_task_ids,suggested_action`。提示严重程度为 `info/warning/error`。证据引用保存可定位的需求、决策、任务、事件或产物 ID，涉及版本时一起保存。格式、权限、状态流转和依赖由服务端验证。提示通过快照给前端呈现，不直接触发写操作。
